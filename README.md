# Gamebit

Your game library and playtime tracker. Build a library, log your hours, rate games, import your Steam library, and follow other players.

## Features

- Search games (powered by IGDB) and add them to your library, or browse the most popular, highest rated and newest releases
- Track status, playtime, ratings and reviews per game; rate from half a star to 10, in halves
- Log play sessions, backdate them, and edit or delete them later
- Import your Steam library; new Steam playtime becomes play sessions on its own; achievement progress for every Steam game, on your profile and other members'
- Year in Review: your year of play by month, game, platform and genre
- Custom lists of games, private or public; "What should I play next?"; wishlist release alerts
- Export your library and sessions as CSV, and import a library from a CSV file
- Share links to games, profiles and public lists
- Follow other players and browse their libraries; discussion boards
- Report profiles, photos, lists, reviews and posts, and block members everywhere in the app (see *Moderation*)
- Offline support: the library is cached locally and edits made offline sync when you reconnect
- Sign in with Google, Apple (iOS) or an email and password, with optional two-factor authentication (an authenticator app)

## Tech stack

- **App:** Flutter / Dart (Android, iOS and web; the Linux desktop build is for debugging)
- **Backend:** [Supabase](https://supabase.com) (auth, Postgres, Edge Functions)
- **Edge Functions** (`supabase/functions`): `igdb-handler`, `game-news`, `game-prices`, `send-notifications`, `check-prices`, `discussions`, `sync-steam`, `sync-achievements`, `steam-link`, `delete-account`, `mfa-recovery`, `admin-moderation`. Third-party API credentials (Twitch/IGDB, Steam) live server-side only.

## Getting started

Prerequisites: the [Flutter SDK](https://docs.flutter.dev/get-started/install) (see `pubspec.yaml` for the required SDK version). The Linux desktop build also needs libsecret and jsoncpp (`sudo apt install libsecret-1-dev libjsoncpp-dev`), which `flutter_secure_storage` links against.

```bash
flutter pub get
flutter run
```

Run the tests:

```bash
flutter test
```

### CI/CD

GitHub Actions (`.github/workflows`):

- **CI** (`ci.yml`) runs `flutter analyze` and `flutter test` on every pull request and push to `main`, type-checks the Edge Functions with `deno check`, and runs the shared helpers' tests (`deno test supabase/functions/_shared/`).
- **Deploy Supabase** (`deploy-supabase.yml`) applies new migrations (`supabase db push`) and deploys the Edge Functions when `supabase/` changes on `main`, or when started by hand. It needs the repository secrets `SUPABASE_ACCESS_TOKEN` and `SUPABASE_DB_PASSWORD` and the variable `SUPABASE_PROJECT_ID`. It runs in the `production` environment, where you can require a reviewer before migrations touch the live database.

### Database migrations

`supabase/migrations` builds the whole database from nothing, in file-name order: `20261011000000_base_schema.sql` creates the tables the project started with (they were first made in the dashboard), and every later file builds on it. `supabase db reset` (locally) or `supabase db push` (a new project) applies them all.

A migration's name starts with its UTC timestamp, and `supabase db push` refuses a new file that sorts before one the database already has. Name new ones with `supabase migration new <what_it_does>`; CI (`ci.yml`, *Check migration names*) fails on a file dated in the future or two files with the same timestamp.

**The live database differs from the files in one place:** its `public_user_games` view had a `custom_cover_url` column the migrations never made. `20261019015200_completion_dates_reviews_release_dates.sql` drops and recreates the view, so it no longer has that column.

**Limits** (`20261019013500_value_limits_and_atomic_deletes.sql`): the database refuses hours below 0 or above 100 000, ratings outside 0 to 5, prices outside 0 to 100 000, reviews over 2 000 characters, session notes over 1 000, and sessions dated more than a day ahead; values already saved out of range were moved into it. Removing a game from the library is one call, `remove_library_game`, which deletes its sessions and the library row in one transaction (`clear_library` does the same for the whole library).

**Ratings** are half a star to ten, in halves, in the app (0 is not rated), and still 0 to 5 in the database: the column is `numeric(2,1)` (made in the dashboard, not the `real` of the base schema) and Postgres refuses to change the type of a column that views read, so nothing in the schema changed for the ten stars: the column, its check and the functions that return a rating are as they were, and a build from before reads the same rows. The app converts in one place, `_stars` and `_ratingToDb` in `lib/services/repository/row_mappers.dart`, and in `CommunityRatings.fromRow` for `game_review_stats`. Half a star is a quarter of the database's scale, which one decimal can't hold, so it is kept to the tenth (0.5 stars as 0.3, 7.5 as 3.8, 10 as 5.0) and read back as the nearest half star, which gives the same rating every time. `20261102234500_community_rating_half_stars.sql` replaces only the body of `game_review_stats` so its average reads each rating back to its quarter (it averaged ratings rounded to a whole star, so 7.5 counted as 8); its answer keeps its shape, the average out of 5 and ten `half_stars`, a half star counted under the star above it, and so do the chart on a profile (`LibraryStats`) and the Reviews panel. `LocalCache` is at version 2 for the new scale: the older entries are dropped and read again. `StarRating` takes half a star from the left of a star, draws the ten stars and shrinks them to fit a narrow place; where even that is too small (the photos in a game's Friends panel, the bubble of the ratings chart) it is a star and the number. Gamebit's library export names its rating column `rating_out_of_10` (to the half star), so it can't be read back as a score out of 5.

### Edge Function errors

The functions answer a failure with `{ "error": "...", "code": "...", "retry_after": 60 }` and a `Retry-After` header when waiting helps. The app turns the `code` into a message (`lib/services/sync_failure.dart`): rate limiting or downtime at Steam or IGDB shows **Sync Delayed** on the Profile tab, and a sync that IGDB only got part of the way through reports the games left for the next one in `delayed`.

### Rate limits

Steam, IGDB and Twitch answer HTTP 429 when they are over their limits. The functions retry a 429 with exponential backoff and jitter (`supabase/functions/_shared/backoff.ts`), waiting for the `Retry-After` the API sent when it is short. The waits are capped so a request never hangs: a search retries for about 3.5 s, an achievements load for 6 s. A limit that outlasts the retries is reported as `*_RATE_LIMITED` with `retry_after`, and `igdb-handler` then answers further searches from the same instance with that error for up to a minute without calling IGDB.

Each member also has limits of their own, so one account (or a script with its token) can't use up the shared quotas: 200 `igdb-handler` requests a minute, 10 manual Steam syncs an hour, 100 achievement loads in 10 minutes, 10 Steam sign-ins (`steam-link`) an hour, 60 `game-news` requests a minute, 30 `game-prices` requests in 10 minutes, 5 new discussion threads an hour and 20 discussion replies in 10 minutes, 10 account deletion attempts an hour, 300 `admin-moderation` requests in 10 minutes, 10 sets of new two-factor backup codes an hour and 5 tries of a backup code an hour (`mfa-recovery`; see *Security*) (`supabase/functions/_shared/rate_limit.ts`, counted in the database by `consume_rate_limit`). Over a limit a function answers `RATE_LIMITED` (429) with `retry_after`. A limiter that can't be reached lets the call through, except for backup code tries, which it refuses until it can count them again.

### Row ownership

`profiles`, `user_games`, `log_entries` and `social_follows` carry restrictive RLS policies for INSERT, UPDATE and DELETE (`20261017120000_enforce_row_ownership.sql`): a signed-in member can only write rows whose owner column is their own `auth.uid()`, whatever other policies exist on the table. The migration fails if a table ends up without them.

### Public profiles and followers

Tapping a member in **Search > Users** (or in a follower list) opens their profile, laid out like your own: photo, name, bio, followers and following (one screen with a tab for each), their favorites, latest play sessions, playtime, the four status boxes (each opens their library), hours per platform, a ratings chart and a short menu into their library, wishlist and follow lists. Steam, if they connected it, is a small icon above the bio that opens their Steam profile. Your own Profile tab is the same page built from your live library, with **Edit Profile** and **Settings** under the counts and **Sign out** at the top right beside your name. You connect and disconnect Steam (and sync your Steam library) under **Settings > Account > Connect accounts**; Steam is connected by signing in through Steam (see *Security*). Their **Library** screen is the same screen as yours (tabs per status with counts, search, platform filter, sorting, grid or list). The Followers and Following counts on your own Profile tab open the same two-tab screen.

All of it is read through views and functions that name their columns, never from the `profiles`, `user_games` or `log_entries` tables, which stay own-row only: `public_profiles`, `public_user_games`, `public_followers`, `public_following`, `public_recent_activity` and `public_profile_stats` (`20261017140000_public_profiles_and_social_graph.sql`, then `20261101050000_verified_services_only.sql` for the current columns of `public_profiles`). What other signed-in members can see is listed in the migration headers and in `docs/privacy.html`: the profile header including bio and Steam ID (the link needs it), the library without purchase prices, and the latest sessions without their notes. Never exposed: email, purchase price, session notes. Achievements show as counts: the profile loads `public_achievement_totals` (unlocked out of all, over every game) and `public_achievement_summary` (every game with at least one achievement unlocked and how far they got, most complete first, up to 500), both read from count columns, never from the lists. Tapping a game opens its achievements in a dialog (search, all / unlocked / locked, Steam's share of players who have each one). The list comes from `public_game_achievements` when the one stored matches the game's counts, otherwise from Steam through `sync-achievements`, which may load another member's game too (see below). These are `SECURITY DEFINER` functions that need a signed-in caller, because RLS works on rows and letting members read each other's `user_games` rows would hand over the `achievements` column too.

**Where the `public_*` views live (`20261022200000_invoker_views_over_private_schema.sql`).** They have to run as their owner, because `profiles`, `user_games` and `log_entries` are own-row only. The definer views are in the `private` schema, which the API does not expose (never add it to the Exposed schemas), and `public.public_profiles`, `public_followers`, `public_following`, `public_user_games` and `public_recent_activity` are plain `security_invoker` views over them, so the app's requests and the Supabase advisor's "Security Definer View" check both see only the thin ones. To change a view's columns, `create or replace view private.<name>` and then `create or replace view public.<name> with (security_invoker = true) as select * from private.<name>`; a migration that makes the `public` one a definer view again brings the advisor's error back.

A game's screen has a **Friends** panel: which of the members you follow completed the game, are playing it or want to play it (To Play and Wishlist together), each as their photo (tap to open their profile) with the rating they gave, if any (a star and the number: ten stars are wider than the photo). It is one call to `following_game_activity` (`20261018170000_friends_on_game_screen.sql`), which returns up to 20 members per status, rated first, and the full count of each; it exposes nothing `public_user_games` doesn't already. Dropped is left out, and the panel is hidden when signed out or when none of them has the game.

Home has a **From people you follow** row: what the members you follow did lately, newest first, as the game's cover (tap to open the game) with the member's photo on its corner (tap to open their profile) and what they did: "+2h · 3h ago" for a session (the latest of each game), "Completed", or "Rated 9" for a game rated but not completed. It is one call to `following_recent_activity` (`20261018220000_following_recent_activity.sql`), at most 30 items (the server caps it at 100), and exposes nothing `public_recent_activity` and `public_user_games` don't already. A completion or a rating carries no time on screen: the only date other members can see is when the game was added to the library, which is what orders them. `FriendsFeedStore` keeps it in memory, lets Home ask again once it is five minutes old, and drops it on sign-out; the row is hidden when signed out, when the request fails or when none of them did anything.

### Achievement counts

`user_games` keeps each Steam game's `achievements_unlocked` and `achievements_total` (`20261018160000_steam_achievement_counts.sql`). Every Steam sync (by hand or in the background) counts the games played since they were last counted, one `GetPlayerAchievements` request per game (Steam has no call that answers for many games with a Web API key), six at a time, most recently played first. `achievements_playtime` remembers the playtime at the count, so a game not played since is not asked about again. A sync counts at most 400 games (60 in the background) and stops starting new requests 125 s in (40 s in the background), on a Steam 429 or on a private profile; the rest is counted on the next sync, and counting never fails a sync. A trigger keeps the counts in step whenever a full list is written to `achievements`, and sets `achievements_synced_at`.

`sync-achievements` takes an optional `user_id`. With another member's id it loads that member's list for the game from the Steam ID on *their* profile (the request can't name a Steam ID), saves it on their row and answers it; a list fetched in the last 10 minutes is answered from the row without asking Steam, so viewers can't make it hammer Steam. That is what Steam shows anyone on their public Steam profile, and what `public_game_achievements` already hands out once stored. Apply the migration, then deploy `sync-steam` and `sync-achievements`, then ship the app. Existing members see every game after their next Steam sync.

The numbers on a profile (games per status, hours, hours per platform, the ratings chart) are worked out in the app by `LibraryStats` from a few columns of the member's library (a page of 500 at a time), the same code that serves your own profile. The member's whole library, with covers, is read only when their Library screen opens. The state lives in `PublicProfileStore`, `PublicLibraryStore`, `SocialGraphStore` and `PublicAchievementsStore` (`lib/state/`), which keep their data in memory only and drop it on sign-out; none of them touches `ProfileStore`.

**Only accounts the app can prove are connected, and that is Steam alone** (`ConnectedService` has one value). PlayStation, Xbox, Nintendo, Discord, Instagram and Twitch used to be names a member typed in and nothing checked, so anyone could claim someone else's account; they are gone, together with the `profiles` columns that held them (`psn_id`, `xbox_id`, `discord_id`, `instagram_id`, `twitch_id`, `connected_services`; `20261101050000_verified_services_only.sql`), and `ProfileStore` deletes what older builds left on the device. Checked 2026-11-01, so no console account can be verified in a way that is both legal and ban-safe today: Sony documents no self-serve sign-in for third-party apps (the one community route, pasting the account's NPSSO cookie, relies on a non-public API and, in the words of the `psn-api` package, is equivalent to a password); Microsoft's `XboxLive.signin` scope for a custom Azure app is reported in Microsoft Q&A threads to be refused (403) unless the app is registered in the Xbox developer programme (ID@Xbox), and the documented Partner Center sign-in is for published Xbox titles; Nintendo has no public account API. These are community reports and vendor docs, not a ruling on any terms of service, so read the provider's current terms before reopening this. Add a service to `ConnectedService` only together with a sign-in the provider documents for third parties, and update `docs/privacy.html` in the same change.

### Background Steam sync

pg_cron calls `sync-steam` every 15 minutes (`20261017130000_background_steam_sync.sql`). It refreshes the libraries of members who have synced by hand before, were active in the last 30 days and are due (12 hours after their last sync; failures back off), ten per run. The job does nothing until you run the one-time setup at the top of that migration: three Vault secrets (`project_url`, `anon_key`, `cron_secret`) and the function secret `CRON_SECRET` with the same value as `cron_secret`. Pause it with `select cron.unschedule('sync-steam-background');`.

### Account deletion

**Settings > Account > Delete account** (required by the App Store and Google Play) asks for confirmation, then calls the `delete-account` Edge Function. It identifies the caller from their JWT and, using the service role, removes their avatar files, log entries, library, follows (both directions) and profile, clears `created_by` on catalog games they added (the games stay for other members), and finally deletes the Supabase auth user. The identity goes last, so a failure part way leaves an account that can still sign in and retry. The app then signs out and erases everything it held on the device for that account (saved copy, queued offline edits, service names). It needs no extra secrets.

**Game details.** Opening a game asks `igdb-handler` (`mode: "details"`, by IGDB id) for its whole page: the exact release platforms (PS3 and Xbox 360 are two platforms, as on IGDB), genres, themes, game modes, player perspectives, game engine, main developers, publishers, storyline and similar games. The details screen shows them, and the exact platforms and genres also replace what the library held, so "Played on" offers exactly the platforms the game is on. The stable part (platforms, genres, themes, modes, perspectives, engines, developers, publishers) is saved on the game's shared `games` row by the function, at most once a week, and the Library filters read it (next paragraph); storyline and similar games change over time and are only kept in memory. The time to beat panel shows the median of the times Gamebit players reported (once enough have) and links to the game on HowLongToBeat. It is a link only: HowLongToBeat (Ziff Davis) forbids automated access to its data (`robots.txt` disallows `/api` and says scraping needs written permission), so the app never fetches from it. Games nobody has opened yet (a library imported from Steam before this, say) are filled in the same way in the background: after the library loads, and after a Steam sync, the app lists the library games whose `games` row was never filled in (`igdb_synced_at` is NULL, a separate query that returns only those ids, so the library payload does not grow) and sends them to `igdb-handler` (`mode: "backfill"`, up to 50 IGDB ids, one IGDB request) 25 at a time, two seconds apart. The function writes each due row as `details` does and answers each game's exact platforms and genres, which the library shows right away. On `IGDB_RATE_LIMITED` / `IGDB_UNAVAILABLE` the app waits the `retry_after` it is given and carries on; any other failure ends the run until the next load (`lib/state/catalog_backfill.dart`). Apply `20261018150000_igdb_game_details.sql` and redeploy `igdb-handler` before shipping the app build; platform names live in `GamePlatform` (`lib/models/game.dart`) and must stay in step with `lib/services/game_api_service.dart` and `supabase/functions/_shared/platforms.ts`.

**Library filters.** The filter icon in the Library header (badged with how many things are picked) opens a sheet to narrow the library by platform (one), and by genre, theme, game mode, player perspective, engine, developer and publisher (any number of values of each: a game needs any one of an attribute's picked values and a match in every attribute picked). Each list holds only the values at least one of your games has, most common first with a count, and a long one (developers, publishers) shows its first values with "Show all" and a search box. What is picked shows as removable chips under the title, and the sheet and the empty state say so when picks leave games out. Genres and platforms are on the games the library already loads. Themes, modes, perspectives, engines, developers and publishers are not: adding six lists to every game would grow the library payload and the copy saved on the device (the part that is already slow to read) for something most visits never use. `LibraryAttributesStore` (`lib/state/library_attributes_store.dart`) reads them in one separate paged query (`CheckpointRepository.fetchLibraryAttributes`: `user_games` joined to `games` for the rows with `igdb_synced_at` set, those six columns only) the first time the sheet opens, keeps them in memory until the account changes, and reads again on the next open after `LibraryStore` reports that the server filled in rows (a game's screen opened, a backfill batch). A game whose row was never filled in has no values yet, so those filters leave it out; the sheet, the chip row and the empty state say how many games that is, and it shrinks as the background backfill and the game screens fill rows in. Another member's Library screen keeps its platform menu only.

### Play sessions

A session is logged from the Quick Log sheet (with **When** to backdate it), or from **Log Hours** on a game (the difference becomes a session). Tapping a session on a game's screen (or under *See all*) edits its hours, platform, day and note, or deletes it with Undo; the game's total moves with it. Edits and deletes made offline are kept and sent later, like any other edit (`PendingEdits.logEdits`, `logDeletes`).

**From Steam** (`20261019014800_steam_playtime_sessions.sql`, `supabase/functions/_shared/steam_sessions.ts`): `sync-steam` keeps the Steam playtime it saw on each library row (`steam_playtime_minutes`). When a later sync (by hand or the background one) sees more, it logs the difference as a session with `source = 'steam'`, dated when Steam says the game was last played; under 5 minutes waits for the next sync. The first playtime seen for a game is its history, so it is only recorded. Members can't set `source` themselves (a trigger keeps it).

### Year in Review

Profile > **Year in Review** works out a year on the device (`lib/models/year_review.dart`) from the sessions and the library: hours, sessions, games, days played, the longest streak, hours by month (with a table view), the most played games, platforms and genres, and the games completed that year. `user_games.completed_at` is kept by a trigger when a game is marked completed (`20261019015200_...`); games completed before it existed count in the year they were last played.

### Reviews, lists and the picker

**Reviews** (`20261022120000_game_reviews.sql`): a review (2 000 characters) under your rating on a game's screen, which every signed-in member can read. The game's **Reviews** panel shows the community rating (the average and how many gave each star, `game_review_stats`) and the first reviews, the members you follow first; **See all** opens every review (`game_reviews`, paged), ordered friends first, newest, highest or lowest rated, or only those of the members you follow. A review can be reported (spam, abuse or something else) or its author blocked: the report is written to `review_reports`, which nothing in the app reads back (moderators read it in `moderation.open_reports`, see *Moderation*), and the review no longer shows for the member who reported it. A review is refused when it has a word the chat rules refuse (SQLSTATE `CP422`). `user_games.reviewed_at` dates a review, kept by a trigger.

**Wishlist prices** (`game-prices`, [IsThereAnyDeal](https://isthereanydeal.com)): a wishlist game's screen has a **Price** panel (the best current price, the cut, the store, the lowest price the game has ever had, when the sale ends and a button to the store's page), and Home has a **Wishlist Deals** row of the wishlist games that are on sale, the ones at their lowest price ever first, then the biggest cut. `WishlistPricesStore` asks for the wishlist games that have no price or an old one (3 hours) once the library has loaded and whenever the wishlist changes, 50 games a request; a failed request is not repeated for 5 minutes, and a game with no price (not on sale anywhere, a console-only game, one IsThereAnyDeal does not know) shows nothing. The app sends the function only the games' catalog ids and the device's region (`PlatformDispatcher.locale`, "US" without one), which picks the currency; if IsThereAnyDeal refuses the region the function answers in US dollars. The function (`supabase/functions/game-prices`, helpers in `_shared/game_prices.ts`) finds each game's IsThereAnyDeal id from the catalog row (`games.steam_app_id` when it has one, in one batch call, otherwise an exact title match: a lookup, then a search that accepts only a result whose title is the same once case, accents, marks and punctuation are ignored: a price of the wrong game is worse than none), saves it on the row (`games.itad_id`, `itad_checked_at`; a game IsThereAnyDeal did not know is asked about again after a week), and takes the cheapest price from Steam, GOG, Epic, Humble, GreenManGaming and Fanatical (`PRICE_SHOPS`; the key resellers IsThereAnyDeal also tracks are left out). A warm instance keeps a price 2 hours and serves the copy it holds if IsThereAnyDeal fails. The title comes from the catalog row, never from the caller, so a member cannot make a game look like another one to everybody. Games from search usually have no Steam app id (Steam sync sets it), so most match by title; reading it from IGDB's `external_games` (as `sync-steam` does) would match more. IsThereAnyDeal's terms ([docs.isthereanydeal.com](https://docs.isthereanydeal.com), read 2026-11-06): prices and links are shown unchanged (no price rounded, no affiliate tag removed), the app links IsThereAnyDeal ("Prices from IsThereAnyDeal" on the panel, and in `docs/`), nothing may suggest an affiliation, the app must not compete with IsThereAnyDeal (a library tracker that shows its prices is the use its API is for, but it is yours to judge), and commercial use needs the app to be public. The limit is 1000 requests in 5 minutes for the whole project. **Before it works:** create an app at [isthereanydeal.com/apps/my](https://isthereanydeal.com/apps/my/), `supabase secrets set ITAD_API_KEY=<the API key, not the OAuth client id or secret>`, apply `20261107000000_game_prices.sql` and deploy the function, then ship the app (without the secret the function answers `NOT_CONFIGURED` and the app shows no prices). It is disclosed in `docs/privacy.html`: change them together. Not built: price-drop notifications (they need server push, with FCM/APNs and stored device tokens, and a privacy-policy change), a target price per game, and prices for games outside the wishlist.

**Push notifications** (Firebase Cloud Messaging): Settings > **Notifications** has a **Push notifications** switch for this phone and, once it is on, one for **Price drops** (a wishlist game goes on sale) and **Replies** (someone replies to a thread you started); release day reminders stay the local ones above. `PushStore` asks the system for its permission when the switch is turned on, takes the phone's FCM token (`PushService`, `FirebasePushService` on `firebase_messaging`) and registers it with `register_push_device(token, platform, language, country)`; turning it off, or signing out (`AuthStore.onLogOut`, waited for 4 seconds at most), calls `unregister_push_device` while the session still works. A token belongs to one member: registering it moves it, so a phone never keeps getting the previous member's notifications. Whether this phone is on is kept on the device per account (`push.v1.<id>`) and checked again at start (a revoked permission turns it off; the token, language and region are registered again); what the member wants is `notification_settings` (own row, both on until turned off). A tapped notification opens its game (`GameLink`) or thread (`ThreadLink`, `/thread/<id>`) through `SharedLinkStore`; a notification that arrives while the app is open is shown by the app itself on Android (`FirebasePushService`, through `flutter_local_notifications` in the same channel; an iPhone shows it itself), and a tap on it opens the same screen (`NotificationTaps` is the one callback the plugin has, shared with the release day reminders).

**Where the notifications come from** (`20261107120000_push_notifications.sql`): a queue, `notification_outbox` (service role only), that two things feed and one drains. A reply feeds it from the `discussion_posts_notify` trigger (`private.queue_reply_notification`): the member whose post was answered is told "replied to you" (`data.direct`), and the thread's starter of a reply in their thread, unless they are that same member (then one, the direct one); never for your own reply, a member you blocked or who blocked you, a suspended one, a member who turned replies off or has no phone, and at most one a thread and kind every 10 minutes; everyone else in a thread is not told unless they follow it: a **bell in the thread's top bar** sets what the member is told of that discussion (`thread_notification_modes`, `20261107160000_thread_notification_modes.sql`, own rows only; `ThreadNotifications`): the default, **every new reply** (for a thread somebody else started; a follower is told of a reply that is not to them, at most 200 followers a reply, and one that is to them hears it as a direct reply, once), or **mute** (nothing from it, not even a reply to their own post; the thread's starter can mute too); both still follow the Replies switch, blocks, the throttle and the need for a phone; a failure inside the trigger costs a notification, never a post. Price drops feed it from `check-prices` (every 3 hours, `pg_cron`): it asks IsThereAnyDeal (the same code as `game-prices`, `_shared/itad.ts`) about the wishlist games of members who have a phone and price drops on (`price_alert_candidates`), in the region of their latest phone, and announces a sale of at least 15% (or at the lowest price ever) once; the price is remembered in `price_alert_state`, announced again only when it falls to 90% of it or less or the currency changes, and forgotten when the game is back at its regular price (`_shared/price_alerts.ts`). A game IsThereAnyDeal has no id for, or a region it does not answer for, is skipped, never "forgotten". `send-notifications` (every minute) claims up to 200 rows (`claim_notifications`: not claimed in the last 5 minutes, fewer than 5 tries, rows over a week old dropped), writes each in the language of each of the member's phones (`_shared/push_messages.ts`: English, or Russian for a Russian phone), sends it through FCM's HTTP v1 API with a token made from the service account (`_shared/fcm.ts`), removes a token FCM says is dead and leaves a notification FCM could not take for a retry. Both functions are called through `invoke_push_function` with the Vault secrets `project_url` and `cron_secret` and no API key: they have `verify_jwt = false` in `supabase/config.toml` (there is no member session, and the new publishable API keys are not JWTs, so the gateway's check could not be passed), and each refuses a call whose `x-cron-secret` is not the `CRON_SECRET` function secret (the same value as the Vault's `cron_secret`; `sync-steam`'s background run uses the same pair, with the anon key as well). Nothing in a notification but the game's or thread's title and the replier's name leaves the database.

**Before push works** (steps 1 and 2 are done: the Firebase project is `gamebit-9523b` and its values are the defaults in `AppConfig`; 3 to 5 are not): (1) a Firebase project with Cloud Messaging; (2) the project's values in `AppConfig` (`firebaseProjectId`, `firebaseApiKey`, `firebaseSenderId`, `firebaseAndroidAppId`, `firebaseIosAppId`: from `google-services.json` and `GoogleService-Info.plist`) as defaults or `--dart-define=FIREBASE_PROJECT_ID=...` and so on; the app starts Firebase from them at run time, so no `google-services.json` is needed in the build, and a build without them has no push (Settings says so); (3) `supabase secrets set FCM_SERVICE_ACCOUNT="$(cat service-account.json)"` (Project settings > Service accounts > Generate new private key; also set `ITAD_API_KEY` for the price check and `CRON_SECRET`, the same value as the Vault's `cron_secret`: neither existed on the project when this was written); (4) apply the migration and `supabase functions deploy send-notifications check-prices`; (5) for iPhones, upload an APNs key (Apple developer account, Keys > Apple Push Notifications service) to Firebase (Project settings > Cloud Messaging) and enable the Push Notifications capability of the app's identifier: `Runner.entitlements` has `aps-environment` (`development`; Xcode replaces it for a store build) and `Info.plist` the `remote-notification` background mode. **Not verified:** the Android build compiles and the SQL (reply trigger, queue, functions, schedule) was run on a scratch Postgres, and the server code has tests; nothing was sent through real FCM or APNs, and no iPhone build was made (no Mac), so the first test is yours. The token comes from the older `getToken()` API (marked deprecated in `firebase_messaging` 17, which now offers `register()` and a Firebase installation id), because that token is what FCM's `token` field is documented to take; moving to the new API would need that checked first.

**Game news** (`game-news`): Home's **Game news** button opens the News screen. **Latest** is the gaming press for everyone, not only the games in the library: the function merges the public RSS feeds of IGN, Eurogamer, Rock Paper Shotgun, GameSpot, Kotaku, GamesRadar+, Nintendo Life and Push Square (for a Russian app, StopGame, Igromania, Playground.ru and 3DNews; `NEWS_SOURCES` in `supabase/functions/_shared/news.ts`), newest first, with a chip per outlet to narrow it. **My games** is Steam's own news (`ISteamNews/GetNewsForApp`, no key needed) for up to ten library games that have a Steam app id, the ones being played first. The app shows an outlet's name, a headline, the start of the story and a picture, and opens the outlet's own page for the rest; nothing is republished or stored. Each feed is fetched at most every 10 minutes per warm instance (Steam's news every 15) whoever asks, a feed that fails is retried after a minute with the copy held meanwhile, and a language none of whose outlets answer falls back to English. Only signed-in members can call it. It needs no secrets; it is deployed with the other functions.

**Discussions** (`20261022165000_discussions.sql`, the `discussions` function): the fifth tab, in the middle. Seven pre-made boards (General, Game talk, What should I play?, Help & tips, News talk, Off-topic, Gamebit feedback; seeded in the migration, so the owner adds or renames one there, and the app shows its own translation of the ones it knows by id) hold threads that members start: a title and an opening text, optionally about a game (a game's screen has a **Game discussions** panel with a button to start one). Replies are flat, oldest first, and each can answer a post (`discussion_posts.reply_to`, `20261107140000_discussion_reply_to.sql`): every post has a **Reply** button, the box above the field says "Replying to <name>" (with a cancel), and the answer shows that name and the start of the post above its text; a quote is left out for a viewer who blocked its author or reported that post, and a deleted post leaves the reply with no quote. The `discussions` function takes an optional `reply_to` and refuses (404) a post that is not in that thread. A member reads through functions that leave out the threads and replies of members they blocked and what they reported (`discussion_threads_page`, `discussion_thread`, `discussion_posts_page`), reports a thread or a reply (spam, abuse, other: `discussion_reports`, write only, moderators read it in the dashboard), blocks a member (`user_blocks`, app-wide since `20261028235500_moderation_and_blocking.sql`, see *Moderation*) and deletes their own thread or reply. **Nobody writes a thread or a reply directly**: the tables have no privileges for members, and the `discussions` function does it with the service role after it has checked the member is signed in and past two-factor, **counted the rate limit** (5 threads an hour, 20 replies in 10 minutes; a refused post counts too), refused a post with **one of the worst words** (racial slurs and child-abuse phrases only, in Latin and Cyrillic letters and the usual ways around a filter; whole words, so "Pakistan" and "snigger" are fine; `_shared/discussion_filter.ts`, to extend it add a line there and an example to its test), more than 3 links, a wrong length or a repeat of the last post. The app shows the **chat rules** (five short lines, `ChatRulesSheet`) before a member's first post on a device, and from the tab's menu. A moderator removes a thread or reply by deleting its row in the dashboard (`supabase/MODERATION.md`), and sets `locked` or `pinned` on a thread there. Deleting an account removes the member's threads, replies, reports and blocks. Apply the migration and deploy `discussions` before shipping the app build.

**Lists** (`20261019115300_game_lists.sql`): Profile > **Lists**, and the list button on a game's screen. A list holds any catalog game, in the order you drag them into; a public list shows on your profile and opens from a link for any signed-in member, a private one is yours only. 100 lists per member and 500 games per list. Lists need a connection (they aren't kept offline); an edit the server refuses is put back with a message. `merge_game_into` moves list entries when it folds a duplicate game.

**What should I play?** (Home): picks a game at random from your To Play and Playing games (or the statuses and platform you choose), never the same one twice in a row; *Play it* marks it Playing and opens it.

### Wishlist release alerts

`games.release_date` holds the day IGDB gives for a game's first release, written by `igdb-handler` and `sync-steam` with the rest of the catalog row and by the app when it adds a game from search. Home's **Wishlist Releases** row shows wishlist games out in the last 14 days or coming in the next 60, and the app says once (per release, per device) when one came out. Release dates move, so the background catalog fill-in also re-asks for wishlist and To Play games that aren't out yet once their row is a week old.

### Import and export

Settings > **Your data** saves the library and the play sessions as CSV files (any spreadsheet opens them), and imports a library file: Gamebit's own export, or another tracker's with a `title` column and, optionally, status, rating (out of 5, 10 or 100; a column named `rating_out_of_10`, as Gamebit's own export has, is always out of 10), hours, platform and review. Each game is matched on IGDB by its id when the file has one, otherwise by its exact title (and year), a few a second; games already in the library are updated and their hours never go down. Imported hours log no sessions. What can't be matched is listed. Two trackers' files are recognized by their columns (`ImportRow.parse`, `ImportSource`), and the import screen says so:

* **Grouvee** ("Export your collection to a CSV file"): `shelves` (an object keyed by shelf name, or a list of names or of objects with a `name`) become statuses, the furthest along winning (Playing, then Played as Completed, Abandoned as Dropped, Backlog, Wish List); `dates` (a list of playthroughs with `seconds_played`) the hours; `platforms` (an object keyed by platform name) the platform; `release_date` the year; `rating` is read as out of 5. Grouvee's ids are GiantBomb's, so games are matched by title.
* **Backloggd**, through the [Backloggd+](https://addons.mozilla.org/firefox/addon/backloggd-plus/) browser extension (Backloggd has no export of its own; the extension writes a CSV, started from Settings > Data Management): a `Backloggd URL` column, or `In Backlog` together with `In Wishlist`, marks it. The true/false columns `Currently Playing`, `Played`, `In Backlog` and `In Wishlist` become statuses (Playing, then Played as Completed, Backlog, Wishlist, none of them the backlog); `Total Hours` plus `Total Minutes` (the minutes beyond the hours; 60 or more is ignored) the hours, from the first playthrough's when the totals are empty; `Rating` the rating, out of 10 in whole numbers, or in stars out of 5 when any figure in the file has a fraction; `Game Name` and `Review` as they are. Backloggd's own record of whether a played game was finished or dropped is not in the file, so every Played game is Completed.

**What is not verified.** Both readers were written from the tools that make or read these files, not from a real export: Grouvee's from two third-party parsers; Backloggd's from the extension's source (`jolacdev/backloggd-plus`, `features/export/utils/csv.ts`, read 2026-11-06), which gives the exact header and says `Total Hours` and `Total Minutes` are the log's totals but not how the minutes are counted, nor the scale of `Rating` (its test data suggest whole numbers up to 10, which is how it is read). A real file of each, a few rows with their star ratings written down, would settle both. HowLongToBeat and the new Backloggery site are reported to export, but no description of their files was found, so they have no preset: a spreadsheet from them still imports if it has a `title` or `name` column.

### PlayStation import

Settings > **Account** > **Connect accounts** has a **PlayStation** row under Steam's (Connect or Disconnect, then **Sync PlayStation**), which reads the member's own play history and trophy list from Sony **on their phone** and hands the games to the same import as a file (`LibraryImport`: IGDB title matching, the list of what was not found). It is **unofficial**: Sony publishes no sign-in or API for other apps and its terms forbid automated access to PlayStation Network, so it can stop working, or be acted on, at any time, and the risk falls on each member's PlayStation account. The member is told so before signing in.

How it works (the open-source `psn-api` and `PSNAWP` libraries do the same): the app shows Sony's own sign-in page in a web view, catches the link it ends at (`com.scee.psxandroid.scecompcall://redirect/?code=...`, a link of Sony's PlayStation phone app), swaps the code for an access token with the `Basic` credential of that app, and reads `m.np.playstation.com/api/gamelist/v2/users/me/titles` (play time; PS4 and PS5 games only, Sony keeps none for PS3 or Vita), `.../api/trophy/v1/users/me/trophyTitles` (trophies per game) and, per game, `.../trophy/v1/npCommunicationIds/<set>/trophyGroups/all/trophies` plus the member's own `.../users/me/npCommunicationIds/<set>/...` (what each trophy is, and what was earned). The web view's cookies are cleared before and after. The app therefore presents itself to Sony as Sony's own app.

* **Saved sign-in.** Sony's refresh token (about 60 days) is kept in the phone's encrypted storage per Gamebit account (`PsnDevice`, `flutter_secure_storage`: Android Keystore, iOS Keychain), so the next sync signs in without the page. When Sony refuses it, it is dropped and the page opens. It is never sent to our servers. "Forget sign-in" is in the dialog that opens before a sync, and signing out of Gamebit removes it (`AuthStore.onLogOut`).
* **Once a day.** A sync is refused until 24 hours after the last one, counted on the phone (`AppConfig.psnSyncCooldown`; signing out of PlayStation is no way round it). Debug builds have no limit; `--dart-define=PSN_SYNC_COOLDOWN_HOURS=<n>` sets any (0: none). It is a phone-side limit: nothing on the server enforces it.
* **Gentle on Sony.** At between 0.7 and 1.3 seconds (a second on average, at random) between any two requests (`PsnClient.pace`, `paceSpread`); a 429 or an expired sign-in stops the sync at once; at most 100 trophy lists are read per sync (`psnMaxTrophyLists`: 203 requests, about three and a half minutes, in the worst case; the PSNAWP library holds itself to 300 requests per 15 minutes), most recently played first, and only for games the member earned a trophy in and whose progress changed since the list was stored (the phone remembers which, `PsnDevice.storedLists`), so a bigger library fills in over the next syncs. In debug builds the log ends a sync with what it cost (`PsnTraffic`: requests, KB received, statuses).
* **Every game, at once.** The overview Sony answers for the whole library already says, per game, its trophy set and how many trophies of each grade the member earned out of how many. The sync stores that for **every** game (`user_games.trophy_meta`, `TrophyMeta`), so the profile's Trophies card is complete after the first sync without any list read; `public_trophy_summary` adds up from those counts.
* **A game's list when it is opened.** A game whose list the sync did not read (past the cap), or whose list is behind the count, shows a notice and a **Load from PlayStation** button in its trophy dialog: two requests with the saved sign-in (Sony's page when there is none), stored on the game and noted on the phone. It is not the day's sync and has no limit of its own beyond the tap (`loadTrophyListFromPlayStation`).
* **Trophy lists.** Each is stored whole on `user_games.trophies` (jsonb, `lib/models/trophy.dart`; names in the app's language when it was read) and shown like the Steam achievements: on the game's screen (the Trophies card opens `GameTrophiesDialog`) and on the profile (`TrophiesSection`: cups by grade, games by completion, a game's list on tap). A game with trophies has no "100%" switch: they decide it (the import marks it perfected when every trophy, or the Platinum, is earned). Other members read them only through `public_trophy_summary` / `public_game_trophies` (`20261106120000_playstation_trophy_lists.sql`), which honour **Settings > Privacy > Show Trophies** (`profiles.show_trophies`, default on), hidden games and blocks.

* **Off unless the build has the client.** The client is the `Basic` credential of Sony's own phone app (`client id:secret` in base64), the value that the open-source `psn-api` publishes in the `Authorization: Basic ...` header of the token request (`src/authenticate/exchangeAccessCodeForAuthTokens.ts`). `AppConfig.psnClientBasic` holds it: put it as the default there to have the import in every build, or pass `--dart-define=PSN_CLIENT_BASIC=<value>` to one build (a define replaces the default, and an empty one switches the import off). A build with no value has no import and Settings does not show the row. Either way the value is compiled into the app. It is a build-time switch: an app already installed cannot be turned off from here.
* **Phones only** (Android and iOS, `webview_flutter`); not offered on the web or the desktop apps.
* **Where it is.** The PlayStation section of the Connect accounts box (`PlayStationAccount`, set apart from Steam's by a line): its row says Not connected or Connected (with when it last synced, as Steam's says its ID; the PlayStation ID is not known without one more request to Sony); **Connect** opens Sony's page at once (no notice or question first) and keeps the sign-in without reading anything; **Disconnect** asks, then forgets the sign-in on the phone (what was synced stays); **Sync PlayStation** under it (while connected) does the sync. There is no row in Your data any more. A member who has synced gets a small PlayStation icon beside the Steam one on their profile (`ConnectedAccountIcons.playStation`, `public_profiles.psn_synced` from `20261106220000_playstation_synced_flag.sql`): it has a check and no link, and its tooltip says "Synced from PlayStation", **not** "verified", because the server cannot check a sign-in made on the phone and a member could write the data it is read from. It follows Show Trophies: others see it only while they share their trophies.
* **New on the server:** `user_games.trophies_earned` / `trophies_total` (`20261105120000_playstation_trophy_counts.sql`) and, for the lists and the privacy switch, `user_games.trophies`, `profiles.show_trophies` and the two trophy functions (`20261106120000_playstation_trophy_lists.sql`), and `user_games.trophy_meta` with the summary reading it (`20261106180000_playstation_trophy_meta.sql`), and the `psn_synced` column of `public_profiles` (`20261106220000_playstation_synced_flag.sql`). Apply all four **before** shipping the app (it selects `show_trophies` from `public_profiles`). `public_user_games` carries none of it. A Platinum, or every trophy, sets the existing `perfected` flag; a game already in the library keeps its status and platform and only gains hours (never fewer), trophies and the perfected mark (`ImportRow.fillGapsOnly`).
* **Not a connected service.** There is no `ConnectedService` entry and no PSN badge: the data comes from the member's phone, so the server cannot vouch for it (like a CSV import).
* **Tested against the live service only in part:** the sign-in, the token exchange and the two list endpoints answered on a phone with a new, empty PSN account (2026-11-05). The shape of a list with games in it, the per-game trophy requests and the refresh-token sign-in come from the libraries' source and docs until tried with an account that has games; the unit tests (`test/playstation_test.dart`, `test/psn_trophies_test.dart`) use made-up answers.
* **To remove it:** delete `lib/services/playstation/`, `lib/screens/settings/psn_import.dart`, `lib/screens/profile/game_trophies_dialog.dart`, `lib/screens/profile/trophies_section.dart`, `lib/widgets/trophy_tile.dart`, `lib/state/public_trophies_store.dart`, `lib/models/trophy.dart`, `test/playstation_test.dart`, `test/psn_trophies_test.dart`, the import row in `data_section.dart`, the trophy card on the game screen, the Trophies card in `profile_layout.dart`, the Show Trophies switch, the `psn*`, `trophy*` and `*Trophies*` strings, the PlayStation paragraphs of `docs/privacy.html`, and `webview_flutter`.

### Share links

Games, profiles and public lists have **Copy link**. A link is the web app's address with the target after `#` (`https://<web app>/#/game/1942`, `/#/u/<member id>`, `/#/list/<list id>`), so it needs no redirect rules on the host. The web app opens it on load; a profile or list asks to sign in first. The web build knows its own address; for the Android, iOS and desktop builds pass it with `--dart-define=CHECKPOINT_WEB_URL=https://<web app>` (without it they show no share buttons).

### Languages

The app is in English and Russian, and follows the device's language until the member picks one in Settings > Appearance > **Language** (saved on the device). Its strings are in `lib/l10n/app_<language>.arb`, with `app_en.arb` as the template; `flutter pub get` (and every build) generates `lib/l10n/generated/` from them. Widgets read them as `context.l10n.<message>`; stores, services and models, which have no `BuildContext`, read `L10n.current.<message>` (`lib/l10n/l10n.dart`). Plurals and selects are ICU messages, so each language says "1 game, 2 games" its own way, and dates and numbers follow the language through `intl` (`lib/utils/formatters.dart`). The layout uses start and end rather than left and right, so a right-to-left language mirrors.

**Adding a language** is a translation:

1. Copy `lib/l10n/app_en.arb` to `app_<code>.arb` (`de`, `fr`...), set `@@locale`, and translate every value; `languageName` is the language's own name ("Deutsch"), which the picker shows. Keep the `{placeholders}`, and give the plurals the forms the language has (`one`, `few`, `many`, `other`...).
2. Add the code to `CFBundleLocalizations` in `ios/Runner/Info.plist`.

`test/l10n_test.dart` fails while a language misses a message or a placeholder; a message left out still shows in English. A new message goes into `app_en.arb` and every other `.arb`.

**What comes from elsewhere** follows the language too. Genres, themes, game modes and perspectives are IGDB's fixed lists, translated in the `.arb` files (`tagName` in `lib/models/filter_options.dart`); game and studio names stay as they are. Steam achievements come in Steam's own translation: `sync-achievements` takes the app's language (`lang`) and keeps each language's names on the stored list (`_shared/steam_languages.ts`). A game's summary and storyline and a studio's description are machine-translated by DeepL in `igdb-handler` (`_shared/deepl.ts`), once per text and language, and kept in `text_translations` (`20261020170000_text_translations.sql`), so every member gets the stored copy; the screen says so and offers the original. It needs a DeepL API key (the free plan's 500,000 characters a month go a long way, as each text is translated only once):

```bash
supabase db push
supabase secrets set DEEPL_API_KEY=<your key>
supabase functions deploy igdb-handler sync-achievements
```

Without the key the app shows IGDB's English text. Supabase's sign-in emails (confirm, reset password) are set up in the Supabase dashboard, not here, and are in English.

### Releasing

The app id is `com.gamebit.mobileapp` on every platform. After changing it, update the Android and iOS OAuth clients in Google Cloud (package name and SHA-1, bundle id).

**Android signing.** Release builds are signed with the upload key named in `android/key.properties`, which is never committed. Make the key once and keep it (and its passwords) safe:

```bash
keytool -genkey -v -keystore android/app/upload-keystore.jks -keyalg RSA -keysize 2048 -validity 10000 -alias upload
```

Then create `android/key.properties`:

```
storePassword=<the keystore password>
keyPassword=<the key password>
keyAlias=upload
storeFile=upload-keystore.jks
```

`storeFile` is relative to `android/app`. Without `key.properties`, `flutter build appbundle` stops with an error rather than signing the bundle with the debug key (a release APK still builds, debug-signed, for testing on a device).

**Sign in with Apple** (required by the App Store next to Google sign-in) is offered on iOS. In Xcode, give the Runner target your team and the *Sign in with Apple* capability (the entitlement is in `ios/Runner/Runner.entitlements`). In Supabase > Authentication > Providers > Apple, enable it and add `com.gamebit.mobileapp` to its client IDs. Apple shares the member's name only on their first sign-in; the app saves it as their profile name.

## Moderation

`supabase/migrations/20261028235500_moderation_and_blocking.sql`, `supabase/functions/_shared/standing.ts`, `supabase/MODERATION.md` (the moderator's runbook, with the SQL to run), `docs/terms.html`. It answers App Store guideline 1.2: filter objectionable content, let members report it and block abusive members, and act on reports within 24 hours.

- **Filtering.** The discussions function refuses the worst words (racial slurs, child-abuse phrases; `_shared/discussion_filter.ts`). The same filter runs in the database (`private.breaks_chat_rules`) on the other public text: display name, handle, bio, the connected-service names, a review, a list's title and description. A save that fails is refused with `content_not_allowed` (SQLSTATE `CP422`, the field in the error's detail) and the app says so (`lib/services/content_refusal.dart`); a brand-new profile is cleaned instead (a Google or Apple name must not stop a sign-up). Text saved before the migration is not touched: `select * from moderation.flagged_text()` lists it. `filter_sql_test.ts` fails when the SQL patterns drift from the TypeScript filter.
- **Reporting.** Reviews (`review_reports`), discussion posts (`discussion_reports`) and now profiles, photos and public lists (`user_reports`, 20 an hour per member). Each report table has `status` (`open`, `actioned`, `dismissed`), `handled_at` and `outcome`; a member can insert but never set them. `moderation.open_reports` lists every open report, oldest first, with `hours_open` and `overdue` (past 24 hours).
- **Blocking is app-wide.** `discussion_blocks` became `user_blocks`. A block hides the member's profile, library, activity, reviews, public lists and discussion posts from the blocker (`private.hidden_members()` is the one place that says whom, used by the `public_*` wrapper views, `game_reviews`, `following_*`, the discussion functions and the `game_lists` policy), ends any follow between the two and stops the blocked member following back (silently, so a block isn't announced). Blocking is from a profile's menu, a review's menu and a discussion post's menu; `BlocksStore` keeps the list (**Settings > Privacy > Blocked members**) and tells the stores that hold members' data to drop theirs.
- **Suspending a member.** `moderation.suspend_member(id, reason, days)` records the suspension, bans the account in Supabase Auth (`banned_until`, so no sign-in and no token refresh), ends its sessions and hides it from everyone. A token issued before lasts up to an hour, so `public.mfa_satisfied()` (asked by every policy and member-facing function) is false for a suspended member, and the `discussions` function asks `public.is_member_suspended()`. A suspended member who tries to sign in is told so, with the contact address (`user_banned`). `moderation.reinstate_member(id)` undoes it. The `moderation` schema is out of reach of every client role and of the API.
- **Moderating from the app.** The owner, and anyone listed in `moderation.admins`, get **Settings > Admin** (`20261101020000_admin_moderation.sql`, `20261101030000_admin_remove_content.sql`, `supabase/functions/admin-moderation`, `supabase/functions/_shared/admin_moderation.ts`, `lib/state/admin_store.dart`): the queue of open reports (oldest first, overdue ones in red), the suspended members with a **Reinstate** button, and for each report **Remove review / thread / reply / list** or **Clear profile** (after asking, showing what goes), **Suspend…** (a reason and 1, 7, 30 days or until reinstated), **Dismiss reports** or **Mark as handled**. An admin also gets **Suspend (admin)** in another member's profile menu. The app asks the database only `public.am_i_admin()` (an answer about the caller) to decide whether to show the screens; everything else goes through `admin-moderation`, which checks the session and two-factor and counts the rate limit, then calls the `public.admin_*` wrappers: the service role only, each given the caller's id and each asking again whether that member is an admin (`private.is_admin`, false while suspended), so the decision is made in the database alone. They call the same `moderation.*` tools as the SQL editor, record `admin:<id>` as who suspended and the admin's id in each closed report's `outcome`, and never send who reported. An admin can't be suspended from the app (remove them from `moderation.admins` first), nor suspend themselves. **Becoming an admin** is one line in the SQL editor (`supabase/MODERATION.md`). Removing content (`public.admin_remove_content`) empties a review (the rating and the game stay), deletes a thread with its replies, a reply or a list (their reports go with them) and wipes a profile (name, handle, bio, photo, service names); the content must belong to the member the report names, the reports about that review or profile are closed as actioned, and the member's other reported content stays in the queue. Deploy order: the migration, the function (deploy-supabase.yml does both), then the app.
- **Terms.** Sign-in shows "By continuing you agree to the Terms of Use and the Privacy Policy" with links, and Settings > Privacy has them and a way to write to us. The pages are served from `docs/`; the app finds them at `CHECKPOINT_DOCS_URL`.

## Security

What the server enforces, whatever a client sends (the anon key in `lib/main.dart` is public by design; these rules are what protect the data):

- **Row level security** on every table; members write only their own rows (see *Row ownership*), and other members' data is read only through views and functions that list their columns.
- **The game catalog is written by the server only** (`20261019132900_security_hardening.sql`): the app sends an IGDB id to `igdb-handler` (mode `add`), which builds the row from IGDB's answer, so nobody can put their own title or cover on a game everyone sees. Achievements and Steam playtime on a library row are also the server's; a member's writes to them are ignored.
- **Limits on what members type**: numbers, reviews and notes (*Database migrations*), and name, handle, bio and avatar on the profile. An avatar must be a photo uploaded to the project's `avatars` bucket, or a Google account photo, so a profile can't load an image from a server that logs who looks at it.
- **A Steam ID is proved, not typed** (`supabase/functions/steam-link`, `20261019134937_steam_id_from_steam_only.sql`). **Connect** on Steam opens "Sign in through Steam" (OpenID 2.0): `steam-link` hands the app Steam's page with a return address that carries a state it signed (the member's id, where to go next, 10 minutes to finish), and when Steam sends the browser back it checks the state and has Steam confirm the answer (`check_authentication`, sent to Steam's own address). With `STEAM_LINK_CONFIRM_URL` set, it saves nothing yet. It sends the browser to the confirm page (`web/steam-link.html`, served with the web app at that address) with a token it signed over the state and the SteamID64 from `openid.claimed_id`, carried after `#`, good for 5 minutes and never past the state. The page names the Gamebit member the link was started from (handle and display name). It posts the token back only when the person who signed in to Steam presses **Link Steam**, and only then does the function save the ID with the service role, taking it off any other profile. Steam isn't asked a second time, because it confirms an answer once. Without `STEAM_LINK_CONFIRM_URL` (`supabase start`, a backend without the web app), the function saves the ID right after Steam confirms it, as it did before the confirm page existed. A member's own writes to `steam_id` are ignored (clearing it, which is Disconnect, still works), so nobody can import someone else's library and achievements by typing their ID. The web app goes to Steam and comes back to itself with `?steam_link=ok` or an error code; the desktop apps catch the return on a free `127.0.0.1` port; Android and iOS open Steam in an in-app browser tab and read the profile every few seconds until the ID is there (the app has no link scheme Steam could call it back on). `return_to` must be a loopback address or, with `ALLOWED_ORIGINS` set, one of its origins. Steam's return carries no Supabase token, so `supabase/config.toml` turns off the gateway's JWT check for this one function (`verify_jwt = false`, which `supabase functions deploy` reads); the function checks the token itself when a link starts. IDs saved before the migration were typed in and stay until their owner connects the account or the member disconnects; the migration header has the one-line update that makes everyone prove theirs. Someone who starts a link and gets you to finish Steam's sign-in on it, within its 10 minutes, no longer gets your Steam account that way. The confirm page shows their handle, not yours, with a warning, and nothing is saved unless you press **Link Steam**. What it can't stop: someone who links anyway, reading past another member's handle. Supabase serves a function's HTML as plain text on its own domain, so the page lives with the web app. **`STEAM_LINK_CONFIRM_URL` must be set wherever the web app is public**: without it there is no confirm step, and that trick works again. Set to anything but an https (or loopback http) address, Connect on Steam answers that it isn't available. With `ALLOWED_ORIGINS` set, the page's origin must be listed.
- **Two-factor authentication, opt-in** (`20261019135155_require_mfa.sql`, `supabase/functions/_shared/mfa.ts`). Settings > Security > **Authenticator app** turns on a code from an authenticator app (Supabase Auth MFA, TOTP): the setup shows a QR code and the setup key (copyable; on Android and iOS also an *Open in authenticator app* link) and checks the first code, and Supabase then signs the account out on its other devices. After every sign-in (email, Google, Apple, the desktop loopback, a reset link) the app asks for the code over everything (`lib/app/second_factor_gate.dart`) and treats the account as signed out until it is right; **Sign out** there works. The server holds the same line, so the prompt can't be skipped by calling the API with the token from the password alone: while an account with a verified factor has an `aal1` session, restrictive policies on `profiles`, `user_games`, `log_entries`, `social_follows`, `game_lists`, `game_list_items` and avatar uploads let it read and write nothing, the SECURITY DEFINER functions return nothing, and the Edge Functions answer `MFA_REQUIRED` (403). Turning it off asks first and needs a session that entered its code. Accounts without it see no change. App builds from before this change don't ask for the code, so an account that turns it on can't use them.
- **Two-factor backup codes** (`20261019204652_mfa_recovery_codes.sql`, `supabase/functions/mfa-recovery`, `supabase/functions/_shared/recovery_codes.ts`), so a member who loses their authenticator app isn't locked out. Right after the first code, the setup makes 10 one-time codes and shows them with **Copy** and **I saved them**; Settings > Security > **New backup codes** (shown while two-factor is on) replaces them after asking, and the old ones stop working. Making codes needs a session that entered its code (`MFA_REQUIRED` otherwise). A code is 10 characters from `crypto.getRandomValues` (Crockford base32, shown as `7K3QD-M9XHT`; typing forgives case, spaces, dashes and O/I/L for 0/1/1) and is shown once: `public.mfa_recovery_codes` keeps only the SHA-256 of the member's id and the code, and only the service role can use the table (RLS on, no policies, nothing granted to members). The code prompt has **Use a backup code**. `mfa-recovery` (mode `redeem`) is the one thing that accepts the `aal1` session of an account with two-factor on: after the rate limit (5 tries an hour, counted before the code is checked), a code that matches an unused one of the member's, made since their current authenticator app was added, is marked used, every MFA factor of the account is deleted and the other codes go; if the factors can't be deleted the code is given back. The app refreshes its session, which then owes no code, lets the member in, and says two-factor is off and to turn it on again in Settings > Security. **A member with neither the app nor a code** can still be let in by the owner: Supabase dashboard > Authentication > Users > the member > delete their authenticator factor, which turns two-factor off the same way. Deploy order: the migration, then the Edge Functions (deploy-supabase.yml does both), then the app; builds from before it don't offer backup codes.
- **Per-member rate limits** on the Edge Functions (see *Rate limits*); Supabase Auth rate-limits sign-ins and sign-ups per IP.
- **Secrets** (Steam key, Twitch/IGDB credentials, `CRON_SECRET`, the service role key) live only in Supabase function secrets and Vault, never in the repository.
- **CORS**: set the function secret `ALLOWED_ORIGINS` to the web app's origins (comma separated, e.g. `supabase secrets set ALLOWED_ORIGINS=https://<web app>`) so only it can call the functions from a browser. Unset, any origin may, as before; the native apps send no origin and are never affected.

On the device: Android and iOS keep the session's tokens encrypted (Android Keystore, iOS Keychain; `lib/services/session_storage.dart`), and Android excludes the app's files from backups and device transfers. The web app sends security headers (`web/_headers`, for Netlify) that stop other sites from framing it.

**Settings to make in the Supabase dashboard** (`supabase/config.toml` only configures `supabase start`):

- Authentication > Providers > Email: turn on **Confirm email** (otherwise anyone can open an account in someone else's address) and **Secure password change**.
- Authentication > Policies (or Providers > Email): minimum password length **8** or more, require **letters and digits**, and turn on **leaked password protection** (Pro plan). `supabase/config.toml` says 8 for `supabase start`, but the live project's value is only what the dashboard says: check it. The app asks for 8 characters whenever a password is chosen (sign-up, reset, change; `minPasswordLength`) whatever the project is set to; signing in accepts any, so an older account isn't locked out.
- Authentication > Multi-Factor: **Authenticator app (TOTP)** must be enabled (it is by default) for Settings > Security > Authenticator app to work; turned off, the setup says two-factor isn't available.
- Authentication > URL Configuration: list only the exact addresses the app returns to (the web app, `http://localhost:3000` for desktop sign-in). No wildcards.
- Authentication > Rate Limits: keep sign-in/sign-up and email limits low; consider **CAPTCHA** (hCaptcha or Turnstile) if bots sign up (the app would need the widget).
- Advisors > Security Advisor: the "security definer view" warnings for the `public_*` views are intentional (see *Public profiles and followers*); anything else is worth a look.

**Release builds**: build with `--obfuscate --split-debug-info=build/symbols` (`flutter build appbundle --obfuscate --split-debug-info=build/symbols`, the same for `ipa`), and keep `build/symbols` of each release to read its crash reports. Android release builds are already shrunk by R8.

**Crash reports** (`lib/services/crash_reporting.dart`): [Sentry](https://sentry.io), off unless the build is given a DSN, so debug runs and tests send nothing: `--dart-define=SENTRY_DSN=https://...@....ingest.sentry.io/...` (and `--dart-define=CHECKPOINT_ENV=production`, which tags the reports). A report is the error and its stack, the app version and the device model; no account, no breadcrumbs (screens, taps, requests), no screenshots, no performance traces, and emails, ids and tokens in an error message are replaced before it leaves the device (`CrashReporting.scrub`, tested). A failed connection is not reported. Settings > Privacy > **Send crash reports** turns it off per device. In the Sentry project turn on **Prevent Storing of IP Addresses** (Settings > Security & Privacy) so the privacy policy's "no IP address" holds, and upload `build/symbols` of each release (`sentry-cli debug-files upload`) to read obfuscated stacks. It is disclosed in `docs/privacy.html`: change them together.

**Staging and other backends.** The Supabase project is chosen when the app is built, not in the code: `--dart-define=SUPABASE_URL=https://<ref>.supabase.co --dart-define=SUPABASE_PUBLISHABLE_KEY=<anon key> --dart-define=CHECKPOINT_ENV=staging` (`lib/app/app_config.dart`). Without them the build is production. A URL without its key (or the reverse) stops at start-up with a message. `web/steam-link.html` has the function's address in its `FUNCTION_URL`: change it with the web app's.

**The contact address** is in `docs/privacy.html`, `docs/terms.html`, `docs/index.html` and `AppConfig.contactEmail` (`--dart-define=CHECKPOINT_CONTACT_EMAIL=...`): change them together.

**Not done, on purpose**: certificate pinning (Supabase and Cloudflare rotate their certificates, and a pinned app stops working until it is updated; TLS with the system's trusted roots is what protects the traffic), Play Integrity / App Attest (needs a server check of every request and can't cover the web and desktop apps, while the rules above hold whatever client calls the API), and root or jailbreak detection (it protects nothing the server doesn't already enforce, and is easy to bypass). Supabase Auth hashes passwords with bcrypt; the app never sees or stores them.

### Using your own backend

The app ships pointing at the project's Supabase instance with a public anon key, which is safe to expose when Row Level Security is enabled. To run against your own backend:

1. Create a Supabase project and apply the migrations (`supabase link`, then `supabase db push`). The background Steam sync needs its one-time setup (see above).
2. Deploy the functions in `supabase/functions` (`supabase functions deploy`, which reads `supabase/config.toml` for `steam-link`'s JWT setting) and set their secrets (Twitch client ID/secret for IGDB, Steam API key, and `CRON_SECRET` if you want the background sync). `steam-link` works without secrets, but once the web app is public set `STEAM_LINK_CONFIRM_URL` to the address of its confirm page there (`supabase secrets set STEAM_LINK_CONFIRM_URL=https://<web app>/steam-link.html`; see *Security*). The page asks the `steam-link` named in its `FUNCTION_URL`, so point that at your project as well. Behind a custom domain, or under `supabase start`, set `STEAM_LINK_CALLBACK_URL` to the function's public address (`http://127.0.0.1:54321/functions/v1/steam-link` locally).
3. Build the app with your Supabase URL and key (`--dart-define=SUPABASE_URL=...`, `--dart-define=SUPABASE_PUBLISHABLE_KEY=...`; see *Staging and other backends*).
4. Create Google OAuth client IDs and update `lib/services/auth_service.dart`. For iOS, pass `--dart-define=GOOGLE_IOS_CLIENT_ID=...`.
5. For email sign-in, enable Authentication > Providers > Email, and choose whether new accounts must confirm their address first (the app handles both). The links in the confirmation and password reset emails go to the Site URL, or on web to the address that served the app, which must be listed under Authentication > URL Configuration > Redirect URLs. Opening a reset link signs the user in and the app asks for a new password (email accounts can also change it under Settings > Security). Only the web app can receive the link for now: Android and iOS need a deep-link scheme and desktop a way to catch it, and the link must be opened in the same browser that asked for it (Supabase's PKCE flow keeps the verifier there).
